## 2. 요소 스키마

**분해 단위**: 1 요소 = 1 주장 또는 1 검증가능한 사실.
판별 테스트 — **"이걸 반박하려면 몇 개를 반박해야 하는가?"** 2개 이상이면 더 쪼갠다.

```jsonc
{
  "id": "E-0173",
  "label": "발우공양 미쉐린 1스타",
  "statement": "사찰음식 전문점 발우공양이 미쉐린 1스타를 받으며 '전통=고급화'가 허용된 선례를 만들었다.",
  "kind": "case",
  "ownership": "reference",
  "slots": ["S3-C3", "S5-BM1", "S6-RAW"],
  "renderings": [
    {"slot":"S3-C3","angle":"'전통'의 넓은 해석이 이미 통용된 증거 — 합법화 논거"},
    {"slot":"S5-BM1","angle":"국내 종교시설 F&B의 단가 상한 실증"},
    {"slot":"S6-RAW","angle":"사찰음식 파인다이닝이라는 서비스 형태"}
  ],
  "stance": {"C3": "합법화"},
  "polarity": "pro",
  "viability": null,
  "numbers": [
    {"value":"미쉐린 1스타","unit":"등급","context":"발우공양, 조계종 직영","year":null}
  ],
  "derived_from": [],
  "edges": [{"to":"E-0088","rel":"supports"}],
  "confidence": "A",
  "source": [{"file":"문화집회시설-용도변경-법규-및-상업활용-가이드.md","loc":"L476-506"}]
}
```

### 필드 정의

| 필드 | 필수 | 값 |
|---|---|---|
| `id` | ✅ | `E-` + 4자리. **에이전트별 번호대를 배정받아 사용** (충돌 방지) |
| `label` | ✅ | 마인드맵 노드 라벨. **20자 이내**, 명사구 |
| `statement` | ✅ | 한 문장. 주장 또는 사실. 수치를 여기 묻어도 되지만 `numbers`에도 반드시 분리 기재 |
| `kind` | ✅ | `fact` \| `constraint` \| `case` \| `insight` \| `option` \| `service` \| `risk` \| `requirement` \| `asset` \| `actor` |
| `ownership` | ✅ | `own`(봉은사가 실제 보유·해당하는 것) \| `reference`(남의 사례) \| `context`(시장·환경) \| `constraint`(법·계약 제약) |
| `slots` | ✅ | 위 표의 슬롯 ID 배열. **1개 이상**. 여러 섹션에 걸리면 전부 넣는다 (요소 복제 금지) |
| `renderings` | ✅ | `slots`의 **각 원소마다 1개씩**. 그 섹션에서 이 요소를 어떤 각도로 쓰는지 한 줄 |
| `stance` | ⬜ | S3 슬롯을 가질 때만. `{"C1":"특화"}` `{"C3":"합법화"}` 형태. 아래 허용값 참조 |
| `polarity` | ✅ | `pro` \| `con` \| `neutral` — 이 요소가 그 주장/선택을 지지하는가 반대하는가 |
| `viability` | ⬜ | `kind:"service"`일 때만 필수. 아래 참조 |
| `numbers` | ✅ | 배열(없으면 `[]`). `{value, unit, context, year}` |
| `derived_from` | ⬜ | service가 특정 case에서 파생됐으면 그 `id` 배열 |
| `edges` | ⬜ | `{to, rel}`. rel = `supports`\|`contradicts`\|`enables`\|`blocks`\|`precedent_for` |
| `confidence` | ✅ | `A`\|`B`\|`C` — 아래 판정 규칙 |
| `source` | ✅ | `{file, loc}` 배열. **최하층 md 파일을 가리킨다** |

### stance 허용값
- `C1`: `"특화"` \| `"대중화"` \| `"양립"`
- `C2`: `"종교"` \| `"문화"` \| `"양립"`
- `C3`: `"합법화"` \| `"미확정영역"` \| `"합법범위내"`
- `C4`: `"독립"` \| `"상호보완"` \| `"백업전제"`

### viability (kind:"service" 전용 — §8 수렴을 필터 쿼리로 만드는 장치)
그 서비스가 **어떤 선택 아래에서 살아남는가**를 태깅한다. 선택 결과를 기다리지 말고 전량 나열 후 조건만 단다.
```jsonc
"viability": {
  "C1": ["특화","대중화"],     // 둘 다 가능하면 둘 다
  "C2": ["문화"],
  "C3": ["Tier1"]              // Tier1(확실 합법) | Tier2(회색지대) | Tier3(불가)
}
```

### confidence 판정 규칙
| 등급 | 기준 |
|---|---|
| `A` | 원출처 확인 — 공공통계 · 법조문 · 기업 IR · 직접 크롤링 데이터 · 출처 섹션이 완비된 문서 |
| `B` | 2차 인용 — 팩트시트 경유 · 언론 보도 · 출처는 있으나 원문 미확인 |
| `C` | 나무위키 의존 · 출처 섹션 자체가 없음 · 출처 표기가 약함 |

**C 등급으로 선분류할 소스 파일 (무조건 C부터 시작)**
- `bongeunsa-traffic-research.md` (나무위키 의존)
- `39-japanese-temple-business-models-research.md` (출처 섹션 없음)
- `32-european-religious-space-business-models.md` (출처 약함)
- `일본-종교공간-심층리서치.html`

**A 기본값 대조군**
- `종교공간-비즈니스모델-상세팩트시트.md` (출처 표기 최강)
- `39-southeast-asian-religious-space-business-models.md` (출처 완비)
- `90-archive/30-buddhism-brand-analysis/` (수치 검증 로그 보유)
- 법조문·계약서 원문 인용

## 3. 출처 규칙 (중요)

같은 케이스가 **원자료 md → 통합 팩트시트 → 시각화 HTML** 3층에 중복 존재한다.

> **`source`는 반드시 최하층 md를 가리킨다. HTML은 출처로 등록하지 않는다.**
> md = SSOT / HTML = 이미 만들어진 프레임 참조용

예외: 해당 내용이 **HTML에만 존재**하는 경우(예: `일본-종교공간-심층리서치.html`의 신사 복합개발·정기차지권 70년)에는 HTML을 출처로 쓰되 `confidence: "C"`로 둔다.

## 4. 중복 방지 규칙 — case와 service를 섞지 않는다

| 원문 | ✗ 잘못된 분해 | ✅ 올바른 분해 |
|---|---|---|
| "츠키지혼간지는 카페 츠무기·시스이·오피셜숍·파이프오르간 런치콘서트를 운영한다" | 1개 요소 (덩어리) | `case` 1개(츠키지혼간지 = 도심 사원 복합화 사례) + `service` 3개(사원 F&B / 사원 리테일 / 사원 음악프로그램). service는 `derived_from`으로 case를 참조 |

- `kind: case` → **S5에만** 등장 (누가 무엇을 해서 성공했나)
- `kind: service` → **S6에만** 등장 (이 공간에 무엇이 존재할 수 있나)
- 둘은 `derived_from` 엣지로 연결
