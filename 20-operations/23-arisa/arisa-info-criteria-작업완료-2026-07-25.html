01 문제 진단

Before — 분류된 나열

Engine D(LLM)가 보고를 7범주로 분류까지는 했지만, 범주 내부 우선순위와 상위 종합(한 문장 결론)이 비어 items가 "LLM 응답 = 시트 행 순서"로 나열됐다. 정렬은 대표창 렌더링(_prio_rank)에서만 부분 적용 → 팀 브리프·개인 카드·API 소비자는 미정렬 나열을 그대로 받았다.

Reporting OS 6-Layer 정의가 이 병을 정확히 지목한다 — Priority Layer가 빠지면 "10가지 나열 → 그래서 중요한 게 뭐야?"

After — 취합 = 정렬 완료

정보가 모이는 순간 이미 "무엇을 먼저 볼지"가 정해진다. 맥킨지 방법론으로 기준을 규율하고, 결정론적 정렬 규칙으로 코드에 못박았다.

03 코드 반영 — sort_items()

취합된 items를 결정론적 키로 정렬. 기존 상수·함수 재사용, stable sort로 내용 무손실.

  1. 범주 — CAT_ORDER: decision→intervention→risk→support→project→growth→anomaly
  2. 긴급도 — URG_RANK: high→mid→low
  3. impact 신호 — _prio_rank: 결재·승인 > 비용 > 리스크 > 개입 > 기타
  4. 미결 경과 — age_days 큰 것 우선 (오래 방치된 결정이 위로)
직원 보고→ Engine D 분류→ carried 이월→ sort_items ★→ JSON · 대표창 · 팀 · API

build_brief_data·build_team_brief_data에서 정렬 → brief/*.json이 소스부터 정렬되어 모든 소비자가 공유. 주간은 _open_decisions가 impact 순(결재·금전>기한>기타).
