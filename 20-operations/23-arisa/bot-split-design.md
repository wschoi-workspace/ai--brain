# 봇 분할 설계서 — 아리사(분장·보고) / 지원봇(조회·질의)

> 2026-08-09 작성 · 결정 대기 문서
> 근거: 맥미니 실가동 봇 전수 실측 (`daily-report-bot.py` 3,100줄)

---

## 왜 나누는가

대표님이 그은 선은 **"일이 도는 것"과 "물어보는 것"**이다. 그런데 이 선이 기술적 경계와 정확히 겹친다.

| | 성격 | 대화 상태 |
|---|---|---|
| 분장 → 보고 → 완료 환류 | 여러 턴을 주고받는 **흐름** | **필요** (8단계 상태 머신) |
| 규정·프로젝트·회의록·브리프 | 물으면 답하고 끝 | **불필요** |

한 봇에 섞으면 상태가 조회를 잡아먹는다. 실제로 났던 일:

- 8/3 대표님이 `report` 직후 "봉은사 어떻게 돼가?"를 물었더니 **업무 내용으로 저장**됐다. 로그를 보니 라우터에 **도달조차 못 했다** — 상태가 먼저 가로챘다
- 그 세션이 **6일간 갇혀** 있었다. 그 사이 대표님이 뭘 보내도 옛 보고의 확인 단계로 갔다
- `persistent=True`라 봇을 재시작해도 부활했다. 오늘 정리할 때도 프로세스 완전 종료를 확인하고서야 지워졌다
- `conv`를 핸들러 **맨 뒤**에 등록해야 `/meeting`·`/assign` 입력을 안 뺏는다는 제약이 생겼다

넷 다 뿌리가 하나다 — **봇이 사람의 위치를 기억한다.** 무상태화로 억지로 합치려던 걸, 애초에 갈라두면 구조적으로 안 부딪힌다. **조회 쪽엔 갇힐 상태가 존재하지 않는다.**

## 분담

### 아리사 — 분장·보고 (기존 `@Dailywork_report_bot`)

일이 도는 루프 전체. **상태를 쓰는 것은 전부 여기.**

| 기능 | 진입 | 상태 |
|---|---|---|
| 주간분장 등록 | `/assign` | `assign_conv` (3단계) |
| 내 분장 업무·마감 | `/todo` · "내 할 일" | 무상태 |
| 일일 업무보고 | `/report` · 자유 텍스트 | `report_conv` (8단계) |
| 완료 환류·진행률 | `asy:` 버튼 | `sync_conv` (2단계) |
| 매장 마감보고 | 자유 텍스트 자동 판별 | 무상태 (`shared/closing`) |
| 문의·건의 접수 | 그 외 자유 텍스트 | 무상태 |
| 직원 거울(mem0) | 보고 저장 시 자동 | — |

> `/todo`를 여기 두는 이유: 분장의 소비 측이다. "내 할 일 보기 → 그중 하나 보고하기"가 한 창에서 이어져야 한다.

### 지원봇 — 조회·질의 (신규)

물어보는 것 전부. **상태 없음. ConversationHandler를 만들지 않는다.**

| 기능 | 상태 | 근거 모듈 |
|---|---|---|
| 사내 규정 질의 | 구현 완료 | `shared/policy_docs.py` |
| 프로젝트 현황·상세 | 구현 완료 | `assistant_tools.project_list/detail` |
| 회의록 조회 | 구현 완료 | `assistant_tools.meeting_doc` |
| 회의 녹취 → 요약 | 구현 완료 | `assistant_tools.meeting_summarize` |
| 브리프 | 구현 완료 | `assistant_tools.daily_brief` |
| 연차 잔여 | **미구현** (Step 3) | HR 포털 엔드포인트 신설 필요 |

**전부 이미 만들어져 있다.** 새로 지을 로직은 없고, 옮겨 붙이는 작업이다.

## 라우터를 공유하는 이유 — 서로에게 넘겨주기

벽을 세우되 **문을 단다.** 직원이 창을 잘못 골라도 막히지 않아야 한다.

```
아리사에 "연차 며칠 전에 신청해?"
  → 라우터가 policy_question 판별
  → "그건 지원봇이 답합니다 → t.me/<지원봇>"  (링크 한 번 탭)

지원봇에 "오늘 A안 확정하고 발주 넣었습니다"
  → 라우터가 report_submit 판별
  → "업무보고는 아리사에서요 → t.me/<아리사>"
```

`shared/intent_router.py`를 양쪽이 그대로 쓰고, **자기 몫이 아닌 인텐트는 안내로 바꾼다.** 라우터를 복제하지 않는 게 요점이다 — 복제하면 두 개의 진실이 생긴다.

## 배포 구조

기존 봇과 같은 패턴을 그대로 쓴다. 새로 만드는 것은 파일 2개뿐이다.

| 항목 | 아리사 (기존) | 지원봇 (신규) |
|---|---|---|
| 스크립트 | `daily-report-bot.py` | `arisa-support-bot.py` |
| launchd | `com.arisa.daily-report-bot` | `com.arisa.support-bot` |
| 로그 | `/tmp/daily-report-bot.log` | `/tmp/arisa-support-bot.log` |
| venv | `24-second-brain/.venv311` | **동일** (의존성 같음) |
| 토큰 | `DAILY_REPORT_BOT_TOKEN` | `ARISA_SUPPORT_BOT_TOKEN` (신규) |
| 필수 env | `PATH`, `KEYRING_BACKEND=file` | **동일** |

### 🔴 지뢰 — mem0 전역 lock

맥미니에 프로세스를 새로 붙이면 `~/.mem0/migrations_qdrant` **전역 lock 충돌**로 기존 봇들의 기억 기능이 조용히 죽는다. 과거 실제 사고였다(직원 거울이 매일 무작동, `arisa_memory_emp.py:17-21`).

**회피책: 지원봇은 mem0를 쓰지 않는다.** 조회·질의에는 개인 기억이 필요 없다. 나중에 필요해지면 그때 `MEM0_DIR` + `DB_PATH`를 분리한다.

## 옮기는 작업 (아리사 → 지원봇)

오늘 아리사에 붙였던 것을 떼어낸다. **로직은 그대로, 위치만 이동.**

| 대상 | 조치 |
|---|---|
| `cmd_ask` · `/ask` 커맨드 | 아리사에서 제거 → 지원봇으로 |
| `_run_read_tool`의 policy·project·brief·meeting_sum 분기 | 아리사에서 제거 → 지원봇으로 |
| `_fmt_projects` · `_fmt_brief` · `_fmt_meeting_summary` | 지원봇으로 이동 |
| `_fmt_my_work` · `cmd_todo` | **아리사에 유지** |
| 봇 프로필 커맨드 메뉴 | 양쪽 각각 재등록 |

아리사에 남는 자유 텍스트 처리는 **보고·마감보고·문의 3종**으로 좁아진다. 그만큼 오분류 위험도 줄어든다.

## 직원 안내

창구가 둘이 되는 순간 **"어떤 봇을 써야 하지?"가 다시 생긴다.** 이걸 이름과 안내문으로 눌러야 한다.

```
아리사      — 오늘 한 일을 보고하고, 내 업무를 확인하는 곳
지원봇      — 회사에 대해 물어보는 곳
```

각 봇 프로필 설명(대화 첫 화면)에 **상대 봇 링크를 넣는다.** 잘못 들어와도 한 번 탭으로 건너간다.

---

## 남은 결정 2가지

**① 지원봇 이름** — 표시 이름과 username이 필요하다.

| 후보 | 표시 이름 | username 예 | 성격 |
|---|---|---|---|
| A | 아리사 도움대 | `arisa_help_bot` | 계열 관계가 이름으로 보임 |
| B | 아리사 Q | `arisa_q_bot` | 짧아서 호칭이 편함 |
| C | 렌트 데스크 | `rentdesk_bot` | "문의하는 곳"이 직관적, 아리사와 분리 |

**② 텔레그램 봇 생성** — BotFather는 제가 조작할 수 없다. 대표님이 발급해주셔야 한다.

```
1. 텔레그램에서 @BotFather 검색
2. /newbot
3. 표시 이름 입력 (위에서 고른 것)
4. username 입력 (반드시 _bot 으로 끝)
5. 받은 토큰을 알려주시면 나머지는 제가 진행
```

## 일정

| 단계 | 작업 | 기간 | 선행 |
|---|---|---|---|
| 1 | 지원봇 스켈레톤 + 규정 QA | 반나절 | **토큰** |
| 2 | 조회 기능 이관 (프로젝트·회의록·브리프) | 반나절 | 1 |
| 3 | 아리사에서 조회 기능 제거 + 상호 안내 | 2시간 | 2 |
| 4 | 양쪽 프로필·메뉴 재등록, 직원 공지 | 1시간 | 3 |

**순서가 중요하다.** 지원봇이 먼저 동작한 뒤에 아리사에서 떼어낸다. 반대로 하면 그 사이 기능 공백이 생긴다.

## 검증

- 아리사: `/report` 8단계 완주 · `/assign` · `/todo` · 마감보고 분리 · 완료 환류 버튼 — **전부 무손상**
- 지원봇: 규정 4종 질문 + 없는 것 1종(지어내지 않는지) · 프로젝트 · 회의록 · 브리프
- **상호 안내**: 아리사에 규정 질문 → 지원봇 링크 / 지원봇에 보고문 → 아리사 링크
- 기존 봇들 생존: second-brain · basket-ops-bot의 mem0 기억 기능이 죽지 않았는지 (**전역 lock 확인**)
- 배포 후 텔레그램 앱에서 두 봇 이름·메뉴 실제 렌더 확인
